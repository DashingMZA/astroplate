Accessibility is not a feature you bolt on at the end of a project. It is the way a page is built: the elements you choose, the order they appear in, and whether every action works without a mouse. Astro makes the good path easier than most frameworks, because most of your page ships as plain HTML. This guide shows how to use that advantage — semantic HTML first, ARIA only where HTML falls short, and keyboard navigation as a first-class requirement — measured against WCAG 2.2 Level AA.

## What WCAG 2.2 actually asks of you

The Web Content Accessibility Guidelines (WCAG) are the international standard for accessible web content, published by the W3C's Web Accessibility Initiative (WAI). WCAG 2.2 is the current version of the WCAG 2 series: it was published as a W3C Recommendation in October 2023, it is backwards compatible with WCAG 2.1 and 2.0, and the W3C advises using it to maximise the future applicability of accessibility work.

WCAG is organised under four principles, remembered as POUR. **Perceivable**: information must be presentable in ways users can perceive — text alternatives, captions, and enough colour contrast. **Operable**: the interface can be operated by keyboard, switch device, touch, and voice, with visible focus and no keyboard traps. **Understandable**: content and behaviour are predictable — the page language is declared, navigation is consistent, and form inputs are labelled. **Robust**: content can be interpreted reliably by browsers and assistive technologies — in practice, valid semantic HTML.

Each principle breaks down into guidelines, and each guideline into testable success criteria at three levels: A (lowest), AA, and AAA (highest). Level AA is the target most teams aim for, because it is the level referenced by most legislation and procurement. WCAG 2.2 adds nine new success criteria to WCAG 2.1 and removes one, 4.1.1 Parsing. The new criteria most relevant to frontend work are 2.4.11 Focus Not Obscured (Minimum), 2.5.7 Dragging Movements, 2.5.8 Target Size (Minimum), 3.2.6 Consistent Help, 3.3.7 Redundant Entry, and 3.3.8 Accessible Authentication (Minimum).

Two numbers from WCAG 2.2 AA recur through this guide. Normal text needs a contrast ratio of at least 4.5:1 against its background, and large text needs at least 3:1; user-interface components also need at least 3:1. And 2.5.8 Target Size (Minimum) requires interactive targets to be at least 24 by 24 CSS pixels, with limited exceptions such as inline links in a sentence.

## Why Astro gives you a head start

Most accessibility failures in modern web applications trace back to the same root cause: the page that reaches the browser is not the page the developer wrote. Markup is generated by JavaScript after load, interactive elements are rebuilt from generic `<div>` elements, and focus is managed — or not managed — by framework code. Astro inverts that: by default, an Astro page renders to static HTML on the server, with zero client-side JavaScript unless you explicitly opt a component in.

Astro's islands architecture extends the same idea to interactive parts of the page: instead of hydrating the whole page, you hydrate only the components that need client-side behaviour, while the text, header, footer, and navigation stay inert HTML. Read [Astro Islands Architecture Explained: How Partial Hydration Works](/blog/astro-islands-architecture-explained-partial-hydration-works) for how `client:load`, `client:idle`, and `client:visible` decide when an island becomes interactive.

## Semantic HTML: the foundation everything else stands on

Semantic HTML means choosing the element that describes what the content _is_, not what it should look like. A `<button>` is not a styled `<div>`; it is a control that browsers already make focusable, keyboard-operable, and correctly announced. A `<nav>` is not a `<div class="nav">`; it is a landmark that screen-reader users can jump to directly.

Start with the page skeleton: one `<header>`, one `<nav>` for primary navigation, one `<main>` for the page's unique content, and one `<footer>`. Inside `<main>`, use `<article>` for a self-contained post, `<section>` for groupings with their own heading, and `<aside>` for complementary content. Do not wrap everything in `<div>` elements and then add ARIA roles to recover the meaning you threw away.

```astro
<html lang="en">
  <body>
    <a class="skip-link" href="#main-content">
      Skip to main content
    </a>
    <header>
      <nav aria-label="Primary"><!-- navigation --></nav>
    </header>
    <main id="main-content">
      <slot />
    </main>
    <footer><!-- footer content --></footer>
  </body>
</html>
```

### Headings are a map, not a font size

Headings are the most-used navigation aid for screen-reader users: most screen readers offer a shortcut to list every heading and jump straight to one. That only works if your headings form a logical outline. Use exactly one `<h1>` per page, then nest downwards without skipping levels — `<h2>` for major sections, `<h3>` for subsections — and never choose a heading level because you like its default font size.

In Astro this is easy to get wrong in components, because a component does not know where it sits in the page. A card that renders its own `<h2>` is correct on a listing page and wrong inside a section that already has an `<h3>` above it. The fix is to pass the heading level in as a prop. The same discipline applies to the blog post template: the post title is the `<h1>` and the body starts at `<h2>`.

### Lists, tables, forms, and images

A group of links is a `<ul>`; a sequence of steps is an `<ol>`. Screen readers announce list structure — "list, five items" — which gives users a sense of scale before they start reading. A table needs a `<caption>` or an accessible name, `<th>` cells with `scope`, and a `<thead>` for the header row; a table built from styled `<div>` elements is invisible as a table to assistive technology.

Forms are where accessibility failures become task failures. Every input needs a programmatically associated `<label>`, using `for` and `id` or by wrapping the input in the label. Placeholder text is not a label: it disappears when the user starts typing and is not reliably announced. Group related controls with `<fieldset>` and `<legend>`, and connect hints and errors with `aria-describedby`.

```html
<label for="email">Email address</label>
<input type="email" id="email" required aria-describedby="email-hint" />
<p id="email-hint">We will only use this to reply to your message.</p>
```

Astro's `Image` component requires an `alt` attribute, which is the right default: it forces the decision. Informative images get a short alt text that conveys what the image conveys — not "image of a chart" but what the chart shows. Decorative images get an empty `alt=""`, which tells assistive technology to skip them. A linked image takes its accessible name from its alt text, so describe the link destination.

## ARIA: powerful, necessary, and easy to get wrong

ARIA — Accessible Rich Internet Applications, formally WAI-ARIA — is a set of attributes that add role, state, and property information to the accessibility tree when native HTML cannot express it. It was first developed by the WAI in 2008, and it remains essential for tabs, accordions, dialogs, live updates, and custom widgets. But ARIA on its own does not change an element's functionality or appearance: adding `role="button"` to a `<div>` does not make it focusable or keyboard-operable.

That is why the WAI's five rules of ARIA, as documented by web.dev, are worth memorising. One: do not use ARIA if a native element does the job. Two: do not add unnecessary ARIA to HTML — a `<ul role="list">` is redundant noise. Three: every interactive ARIA control must be keyboard accessible. Four: do not hide focusable elements with `aria-hidden="true"`. Five: give every interactive element an accessible name, from its text, its `alt` text, its `<label>`, or an `aria-label`.

The most common ARIA mistake is the opposite of what beginners expect: not too little ARIA, but too much, applied incorrectly. Web.dev's ARIA and HTML guide notes the WebAIM finding that home pages with ARIA present averaged more detected errors than those without it, primarily through improper implementation. Treat ARIA as a precision tool: use the smallest attribute that solves the problem, and test with a screen reader.

### The ARIA you will actually use

Most Astro sites need only a handful of ARIA patterns. `aria-label` gives an accessible name to an icon-only button, such as a menu toggle. `aria-expanded` and `aria-controls` describe a disclosure: a button that shows or hides a panel, with `aria-expanded` updated every time the state changes. `aria-current="page"` marks the current page in a navigation list. And `aria-live` regions announce dynamic content, such as a form success message.

```astro
<button
  type="button"
  aria-expanded="false"
  aria-controls="panel"
  data-disclosure
>
  Show details
</button>
<div id="panel" hidden>
  <!-- panel content -->
</div>
<script>
  document.querySelectorAll("[data-disclosure]").forEach((b) => {
    b.addEventListener("click", () => {
      const p = document.getElementById(b.getAttribute("aria-controls"));
      const open = b.getAttribute("aria-expanded") === "true";
      b.setAttribute("aria-expanded", String(!open));
      p.hidden = open;
    });
  });
</script>
```

The mobile navigation menu is the pattern Astro sites hit most often. The correct shape is a `<button>` with `aria-expanded` and `aria-controls`, a `<nav>` whose visibility is controlled by the `hidden` attribute or a class, and focus that stays in document order — the menu items are ordinary links, and Escape closes the menu and returns focus to the toggle button.

## Keyboard navigation and focus: the test you can run right now

Every interactive element must be reachable and operable by keyboard alone: Tab to move forward, Shift+Tab to move back, Enter to activate a link or button, Space to activate a button or toggle a checkbox, arrow keys where a widget pattern calls for them, and Escape to dismiss a dialog or menu. That is success criterion 2.1.1 Keyboard, at Level A — the lowest bar in WCAG, and the one most often failed by custom components. Put your mouse aside and Tab through your own site: if you cannot reach, locate, activate, or escape something, you have found a bug that blocks real users.

Focus order is the second half of the requirement. The tab order follows the DOM order, so a page whose visual layout is achieved by reordering elements with CSS will tab in a different order from the one a sighted user sees. Keep the DOM order logical and let CSS handle presentation. And never use a positive `tabindex` value to force an order — the only tabindex values a well-built page needs are `0`, for a custom widget in DOM order, and `-1`, for programmatic focus.

### Visible focus is not optional

A keyboard user needs to know where they are, and the only way they know is the focus indicator. Browsers draw one by default, and the most common accessibility regression in a redesign is a global CSS rule that removes it — `outline: none` on `:focus`, usually added because the default ring "looks untidy". Never remove the focus indicator without replacing it with something at least as visible.

The modern pattern is `:focus-visible`, which shows the indicator for keyboard interaction while leaving mouse clicks clean:

```css
:focus-visible {
  outline: 3px solid #2563eb;
  outline-offset: 2px;
  border-radius: 2px;
}
/* Never do this without a replacement: */
:focus {
  outline: none;
}
```

In Tailwind CSS, the same idea is `focus-visible:outline-3 focus-visible:outline-blue-600 focus-visible:outline-offset-2` on interactive elements, or a shared utility class applied once. If you are building that system now, [How to Build a Scalable Website Design System with Astro and Tailwind CSS](/blog/build-scalable-website-design-system-astro-tailwind-css) covers tokens, component structure, and the shared utilities where a focus style should be defined once and reused everywhere. For the responsive side of the same work, see [Building Responsive Websites with Tailwind CSS: A Practical Guide](/blog/building-responsive-websites-tailwind-css-practical-guide).

### Skip links, dialogs, and focus management

A skip link is the cheapest accessibility feature in existence and one of the most useful. It is a link, first in the DOM, that jumps straight to the main content, visible only when it receives keyboard focus. Without it, a keyboard user must Tab through every navigation link on every page before reaching the content. Position the link off-screen, bring it into view on `:focus-visible`, and test it by pressing Tab once after the page loads.

```css
.skip-link {
  position: absolute;
  left: 1rem;
  top: -100%;
  padding: 0.5rem 1rem;
  background: #0f172a;
  color: #fff;
}
.skip-link:focus-visible {
  top: 1rem;
}
```

Dialogs are the other classic focus problem. A modal that opens without moving focus leaves the keyboard user stranded behind it; a modal that does not return focus to the triggering button on close leaves them lost. The native `<dialog>` element, opened with `showModal()`, solves most of this for free: it provides focus containment, Escape handling, and an inert background. If you need a custom dialog, you owe the same behaviour by hand.

## Colour, contrast, and motion

Colour contrast is the most mechanical of these concerns: normal text at 4.5:1, large text and UI components at 3:1. Check the combinations you actually ship — body text, muted secondary text, placeholder text, and button text on the button background. Never use colour alone to convey meaning: a form error shown only in red is invisible to a user who cannot distinguish red, so pair it with an icon and text.

Motion deserves a deliberate decision. Animations and auto-playing carousels can cause nausea or disorientation for people with vestibular disorders, and WCAG's 2.3.3 Animation from Interactions criterion addresses animation triggered by user interaction. Respect the `prefers-reduced-motion` media query, and disable non-essential animation when it is set. Do not auto-play video with sound, and give every video captions and every audio-only clip a transcript.

```css
@media (prefers-reduced-motion: reduce) {
  *,
  *::before,
  *::after {
    animation-duration: 0.01ms !important;
    transition-duration: 0.01ms !important;
  }
}
```

## Testing accessibility in an Astro project

Start with the browser. Chrome DevTools' Lighthouse audit includes an accessibility category that checks contrast, names, ARIA usage, and more, and its accessibility tree inspector shows exactly what assistive technology sees for any element — the computed name, role, and state. Run Lighthouse on every template, not only the homepage.

Then add automated checks to the project. axe-core is the rule engine behind most accessibility tooling, available as a Playwright integration (`@axe-core/playwright`) for end-to-end audits against the built site, and as a Vitest integration for component-level checks. A practical setup is a Playwright test that builds the site, visits each route, runs an axe audit, and fails on violations. For linting, `eslint-plugin-astro` ships accessibility rules adapted from `eslint-plugin-jsx-a11y`, as `jsx-a11y-recommended` and `jsx-a11y-strict` configurations.

Manual testing finds the problems automation cannot see. Unplug the mouse and use only the keyboard for five minutes on each template — can you reach everything, do you always know where focus is, can you complete the form, can you escape the dialog? Then zoom the page to 200% and check that content reflows without horizontal scrolling, which is WCAG 1.4.10 Reflow at AA. Then test with a screen reader: NVDA on Windows and VoiceOver on macOS are both free.

## Frequently asked questions

### Is semantic HTML enough, or do I always need ARIA?

Semantic HTML is enough for most of a page. Native elements already expose the correct name, role, and state, and they come with keyboard behaviour built in. You need ARIA only where HTML has no element for the pattern: tabs, accordions, dialogs with custom behaviour, live updates, and custom widgets. When you do use ARIA, use the smallest attribute that solves the problem and test with a screen reader.

### What WCAG level should a small site aim for?

Level AA. Level A is the minimum and leaves real barriers in place — contrast, focus visibility, and reflow are all AA criteria. Level AAA is aspirational: WCAG itself notes that it is not recommended as a general policy for entire sites. AA is the level referenced by most legislation and procurement, and it is the level this guide's recommendations are calibrated to.

You need both. Axe and Lighthouse catch mechanical problems — missing names, bad contrast, invalid ARIA, heading order — quickly and repeatably, and they belong in your test suite. They cannot tell you whether a page makes sense when read aloud, whether a live region announces at the right moment, or whether a label is accurate rather than merely present. A short screen-reader pass — NVDA on Windows, VoiceOver on macOS — finds those problems.

### What is the fastest accessibility win for an existing Astro site?

Do the keyboard-only pass first. Unplug the mouse, Tab through the homepage, a post page, and any form, and fix what you find: missing skip link, invisible focus, unreachable controls, and dialogs that do not return focus. Those fixes are usually small — a CSS rule, a link, a `showModal()` call — and they unblock the users who are most completely locked out. After that, run Lighthouse and axe on every template and work through the contrast and naming issues they report.
